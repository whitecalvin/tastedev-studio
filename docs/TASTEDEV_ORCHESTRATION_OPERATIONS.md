# 오케스트레이션 운영 고도화 — 사용 안내

## 통합 대기열

팀 작업 공간의 통합 검토함에서 대기 순서와 선행 요청을 확인한다. 같은 원본 프로젝트의 동일 작업 또는 겹치는 경로는 직렬로 검토한다. `통합 우선 처리`는 아직 검토되지 않은 요청의 순서만 바꾼다. 이미 승인·적용된 변경을 앞질러 적용하지 않는다. 순서가 바뀌어도 최신 원본 비교와 새 제안 승인이 필요하다. 실패 뒤 적용 내용이 남았거나 복구 상태가 불명확하면 되돌리기·복구 전까지 잠금을 유지한다. 자동 rebase·자동 승인·commit/push는 없다.

## 장비·역할 정책

프로젝트 오케스트레이션 → 장비·역할을 펼친다. 게시된 관계도의 장비를 선택하고 사용 여부, 구현/배포/테스트 역할, 최대 동시 실행 수(1–8), OS, 선택적 사용 시간을 설정한다. 범위를 확인한 후 정책을 저장한다. 정책이 하나라도 있으면 소속 규칙이 없는 Agent는 새 배정에서 제외된다. 규칙이 없는 기존 프로젝트는 종전 배정 동작을 유지한다. 마지막 규칙 제거도 확인이 필요하다.

소속은 명시적 장비→Agent 관계와 실제 Agent ID를 사용한다. 장비 이름으로 물리 PC를 추측하지 않는다. 실행 역할은 작업으로 연결된 책임 역할을 기준으로 하며 배포 승인 경계는 유지한다. 같은 장비에 선언된 Agent들의 다른 프로젝트 활성 Run도 동시 실행 수에 포함한다. 물리 장비 신원 증명이나 서로 다른 장비 ID의 자동 통합은 제공하지 않는다.

정책은 게시된 관계도 revision/checksum에 고정된다. 관계도를 다시 게시하면 재검토 전 새 배정을 차단한다. 실행 중인 Run을 중단하거나 옮기지 않는다. 시간은 IANA 시간대·요일·시작 분(자정 기준)·종료 분으로 설정한다. 종료 분은 포함하지 않으며 1440은 하루의 끝이다. 한 장비에 하나의 같은 날 시간 구간만 지원한다.

## 선행 성공 스케줄

스케줄러에서 새 스케줄 → 트리거 종류 `선행 작업 성공`을 선택한다. 선행 작업 식별자는 `task:<Factory task ID>` 또는 `run:<Run ID>`이다. 같은 프로젝트에서 Core가 실제 성공/완료를 확인한 항목만 사용한다. 기존 Protocol Test 또는 검토된 Graph 실행 경로를 재사용한다. 활성화 승인은 기존 스케줄 권한과 정책을 따른다.

스케줄 생성 이전 완료·실패·취소는 트리거하지 않는다. 동일 완료 신원은 SQLite 재시작 후에도 한 번만 소비한다. 기본 정책은 10초보다 늦게 발견한 완료를 missed로 기록하고 건너뛴다. 새 실행 정책에서 허용 지연 안의 한 번 실행을 선택할 수 있다. Core 중단 중 지나간 완료를 무한 재생하지 않는다. Git·외부·OS 이벤트는 계속 미지원이며 임의 shell 명령을 받지 않는다. 시간/주기 스케줄은 기존 동작을 유지한다.

## 실행 모니터링과 재배정

실행 모니터링에서 전체/조치 필요/활성 필터, 승인 대기, 실행 대기, 현재 Run 단계와 노드별 Attempt 이력을 확인한다. 단계는 같은 프로젝트의 실제 RunStep에서만 가져온다.

대기열에서 Job을 열면 Core의 현재 권한·실행 능력·장비 정책에 따른 배정 불가 이유를 확인할 수 있다. 대기 작업 배정 검토에서 적합한 Agent를 선택하고 확인한다. Graph 작업은 게시된 후보 Agent 범위 안에서만 재배정하며 자동 배정으로 경계를 해제할 수 없다. 최신 Job 시각과 이력 길이를 비교해 오래된 요청을 거부한다. 최대 재배정은 20회이며 이전 배정/시간/새 배정을 보존한다. 이미 Run이 생긴 작업은 옮기지 않는다.

## 통합 후 다음 작업

실제 통합 Source를 게시한 다음, 후속 idle 계약에서 Source를 다시 검토한다. 관계도가 같더라도 Source·입력·revision이 바뀌면 검토할 수 있다. 이전 계약을 보존하고 draft로 돌아가며 새 queue 승인이 필요하다. 완료된 선행 작업이 검증한 Source 바이트와 다르면 후속 실행을 막는다.

## 검증 경계

실제 ChatGPT 모델과 실제 Rust Agent를 사용한 disposable 파일 3개 통합·원본 재시험·독립 검토를 통과했다. 이전 기록에서는 후속 Source 재검토·승인·Graph 시작까지만 확인했다. product-orchestration-20261031에서는 선행 pricing 수락 이후 별도 totals 후속 작업의 실제 AI 수정·Rust Agent Test·독립 실제 모델 검토·완료까지 확인했다. 파일 생성/삭제/이름 이동은 실제 모델의 산술 수정안과 승인된 통제 relocation 계획을 결합했다. 모델이 세 구조 변경을 자율 생성했다고 주장하지 않는다.

최신 운영 확장 사용법은 TASTEDEV_PRODUCT_ORCHESTRATION.md를 따른다. GUI는 production export와 실제 Dummy Core DB 사본, synthetic Native IPC에서 확인했다. 실제 설치본·Linux 운영 장비·서비스·업데이트 시험은 별도다. 패키징과 설치는 사용자 담당이며 여기서 수행하지 않았다.
