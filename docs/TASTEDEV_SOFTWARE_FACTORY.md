# STUDIO 소프트웨어 팩토리

## 실행 경로

프로젝트 오케스트레이션의 **소프트웨어 팩토리**에서 목적·완료 기준·수정 허용 경로를 작성한다. `AI로 작업 나누기`는 연결한 AI로 실제 소스를 읽고 작업 초안을 제안한다. 기준 번호의 누락, 읽지 않은 경로, 범위 확대, 중복·역방향 의존 관계는 저장 전에 거부한다. 계획을 검토해 초안으로 저장한 후 각 계약을 승인하면 Core가 배정한다. 계획 생성과 초안 저장은 소스를 변경하거나 실행을 시작하지 않는다.

초기 프로젝트는 `팩토리 흐름 초안 추가`로 구현·독립 검토 노드와 서로 다른 AI 프로필을 만든다. 기존 작업 노드가 있는 그래프는 덮어쓰지 않는다. AI 연결·프로필과 그래프를 검토해 저장하고, 실제 테스트가 정의된 저장된 Protocol과 소스를 Core에 게시한다. 구현 프로필은 `verified-fix`, 검토 프로필은 `analysis` 완료 조건을 사용한다. 팩토리 계약은 게시한 그래프 판·그래프/Protocol/AI 입력 체크섬·소스 체크섬을 고정한다.

## 역할과 완료 근거

- 조정자: AI 작업 분할과 결정적인 계약 검증·의존 관계·자원 배정으로 구성한다.
- 구현자: 기존 Graph AI → Proposal → FixService → 승인된 패치 → 실제 원격 TestPlan 경로를 사용한다.
- 독립 검토자: 구현자와 다른 프로필·새 대화에서 허용 범위와 완료 기준, 실제 구현 Run 근거를 읽는다. 검토 노드의 소스 패치는 Core에서 거부한다.
- 인수자: 실제 테스트를 통과한 변경 파일 전체를 검토자가 동일 내용으로 읽었고 근거를 남겼을 때 검토 메모와 승인/수정 요청을 기록한다.

모델의 분석 완료나 `passed`라는 설명만으로 작업이 완료되지는 않는다. 기존 Graph의 Fix 증명은 승인·적용 journal, 실제 성공한 Core Run과 전달 Snapshot, 변경 파일의 결과 해시를 확인한다. 팩토리는 그 증명에 독립 분석의 실행/노드 ID와 읽은 파일 내용의 일치를 추가한다. `completed`는 개발 인수 상태이며 설치본 QA·출시 완료가 아니다.

## 승인과 자동 실행 범위

작업 계약을 승인하면 큐 배정과 해당 계약의 한도 내 AI 분석은 자동 진행한다. AI 분석 실행에는 저장된 작업 공간이 연결된 STUDIO의 오케스트레이션 화면이 필요하다. 화면을 벗어나면 기존 AI 취소/lease·마감 정책이 적용된다. Core만 켜 둔 상태에서 소스 수정까지 무인 실행하는 별도 프로세스는 만들지 않는다.

소스 변경은 기존 내용·파일별 패치 승인과 충돌 검사를 유지한다. 계약 밖 경로와 검토 역할의 패치는 history의 제안/승인 저장 단계에서 차단하므로 파일 쓰기 전 승인 저장에 실패한다. 최종 인수도 사용자가 명시적으로 기록한다. 커푸·운영 게시·서명·패키징·설치 시험을 자동 실행하지 않는다. 이번 구현은 Agent 실행기, AI 제공자, 패키징 파이프라인을 복제하지 않는다.

## 동시성·재시도·재개

- 전체 최대 2개 작업, 프로젝트마다 실행 중인 Graph 1개를 허용한다. 검토·일시 중지·취소 대기 작업은 자원 점유를 유지한다.
- 같은 독점 자원 이름과 같은 프로젝트의 겹치는 상대 경로를 직렬화한다. 수정 허용 경로는 대소문자까지 일치해야 하며, 자원 충돌은 Windows 경로 별칭을 놓치지 않도록 대소문자를 무시해 보수적으로 판단한다. 여러 프로젝트가 동일 저장소/GUI/빌드 자원을 공유하면 `repo:tastedev-common`, `gui:dev-01`, `build:dev-01` 등 같은 자원 키를 계약에 지정한다. 독점 자원 이름만으로 OS 경로나 다른 프로그램의 사용을 감지하지 않는다.
- 선행 작업은 명시적으로 개발 인수를 통과해야 해제된다. 다른 프로젝트의 의존 작업은 읽기 권한을 확인한다. 실패한 의존 관계를 무시하고 진행하지 않는다.
- Graph 생성 전 실행 ID와 intent를 저장한다. 저장 실패 시 배정하지 않는다. 응답 유실 후에는 같은 실행 ID를 조회해 중복 생성을 피한다.
- Core 재시작은 큐/진행 중 작업을 일시 중지한다. 사용자가 계약·권한을 검토해 재개한다. 기존 실행·테스트 근거를 보존한다.
- 실패 단계 재시도는 같은 Graph에서 실패한 활성화만 새로 배정한다. 통과한 구현을 검토 연결 실패 때문에 다시 실행하지 않는다. 계약과 프로필/그래프의 시도 한도를 함께 적용한다.
- 소스나 요구사항에 대한 수정 요청은 기존 근거와 요청 메모를 보존하고 수정한 계약을 새로 검토한다. 통과한 Graph를 단순 재시도하여 소스 변경 요청을 숨기지 않는다.
- 계약 시간 한도는 대기 시간을 포함한다. 만료/취소 시 실제 Graph가 종료될 때까지 자원을 유지한다. 권한 철회는 자동 진행을 일시 중지한다.

## 저장 및 인터페이스

기존 CoreStore의 암호화 SQLite unit `software-factory`에 계약·상태·버전·시도·인수 기록을 저장한다. 메모리 모드에서는 영속 저장이 없음을 화면에 표시한다. 변경은 버전 비교로 동시 갱신을 거부한다. 조회 결과에는 내부 실행 권한 actor를 노출하지 않는다.

인증된 기존 Core RPC `factory`가 `list`, `create`, `create-plan`, `queue`, `resume`, `retry`, `review`, `cancel`을 제공한다. 프로젝트 경계와 기존 팀의 read/history-write/run/approve/cancel 권한을 적용한다. 계획 일괄 저장은 전체 검증 후 한 저장 단위로 반영하며 반복 요청은 동일 계약을 중복 생성하지 않는다.

현재 모델·제공자별 토큰/요청·시간·시도 한도는 기존 AI 예산을 사용한다. 가격 정보가 없는 연결에서 금액 사용을 확정하지 않는다. 별도 worktree 생성·Git 통합·외부 무인 CLI 에이전트 실행은 이 기능이 대신 수행하지 않는다. 기존 소스 경계와 충돌 검사, 사용자가 지정한 공유 자원 계약을 사용한다.

## 검증 근거

실행 결과와 재개 기록은 `resources/verification/software-factory-20261017`에 보관한다. 계약/분할·실제 Graph 서비스·인증된 로컬 RPC/소스 업로드/암호화 재시작 검증과 실제 외부 모델·설치본 검증을 구분한다.
